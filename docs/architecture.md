# Architecture

This page owns current module boundaries and data flow. [Product behavior](product.md), [design conventions](design-system.md), [content management](content-management.md), and [testing](testing.md) own their respective requirements. The [ownership decision](decisions/0001-repository-ownership-and-boundaries.md) explains the rationale; completed work trackers preserve migration history.

## Repository ownership

Keep one frontend package and the existing Python package. Root HTML entry points and tool-discovered configuration stay at the repository root. Use relative imports; introduce aliases only when compiler, Vite, tests, scripts, and boundary checks resolve them consistently.

- `src/app`: learner composition, navigation identity, lazy/preload wiring, and drawer policy.
- `src/features/quizzes`: quiz screens, controls, session coordination, selectors, feedback, results, and celebrations.
- `src/features/flashcards`: flashcard screens, study controls, session coordination, and selectors.
- `src/shared`: theme and reusable presentation under `ui/{shell,loading,transitions,notifications,content,study,catalog}`. Share components with demonstrated reuse or an application-wide responsibility.
- `src/domain`: pure rules, types, and repository interfaces. `src/analytics` owns pure aggregation; `src/persistence` owns storage repositories and codecs. These small boundaries stay flat.
- `src/content`: canonical JSON at the root; stored contracts in `schema`, read-only adapters in `local`, transport/decoders/runtime repositories in `api`, checks in `validation`, and framework-independent rendering policies in `richText`.
- `src/admin`: separate authoring composition and presentation, with independent `core` and `data` boundaries. `src/qa` owns the development content preview.
- `backend/src/meducation_api`: existing read-only Python service. Package metadata is ignored output.
- `scripts/content`: validation/audit CLIs; `scripts/migrations`: candidate-producing migrations; `scripts/architecture`: shared dependency policy and tooling.
- Colocated tests belong to their module. `src/test` supplies test setup; `tests/fixtures` holds shared contracts; `e2e` holds browser workflows and their fixture banks. See [suite ownership](testing.md#suite-ownership-and-fixtures).

Avoid broad barrels, forwarding modules, speculative shared layers, and empty placeholder directories. Maintenance scripts are outside the application graph. Ignored private PDFs, extraction data, and legacy public assets have separate [backup requirements](content-management.md#local-source-material-and-generated-output).

## Checked dependency boundaries

`npm run lint` applies the local `architecture/boundaries` ESLint rule to source modules, using TypeScript resolution for static imports, re-exports, import types, `require`, and literal dynamic imports. Relative path variants and configured aliases resolve to the same owner. Non-literal module paths are rejected because their ownership cannot be checked. The policy and resolver live in `scripts/architecture/boundaries.mjs`; the ESLint plugin and graph command share them.

Domain modules depend only on domain; analytics and persistence depend on their own layer and domain. These layers and content cannot import React/MUI/Emotion. Content depends only on content and domain. Shared presentation uses shared, content, domain, and analytics modules. Features use their own feature and lower-level modules, never app, admin, QA, or sibling features. Concrete storage imports are limited to feature sessions; selectors can use storage contract types. Admin core/data cannot import presentation. App remains the composition root, and admin/QA can use shared rendering and content validation. Browser storage globals and properties are restricted to persistence; tests can exercise storage fixtures.

Tests retain the same ownership rules, with fixture/helper access permitted. One explicit existing exception lets `src/content/validation/bankContract.test.ts` import `src/admin/core/serializeBank.ts` for Python/authoring revision parity. It does not allow other content tests to import admin. Production modules cannot import tests, fixtures, or maintenance scripts.

`npm run check:architecture` checks the whole source/script graph for forbidden edges and runtime cycles, including dynamic edges. Explicit type-only edges are checked for ownership but excluded from runtime cycles. It also follows static runtime edges from learner bootstrap and App to reject eager canonical-bank or validation-pipeline loading; intentional local-adapter dynamic imports remain allowed. This is an import-graph check, not proof of arbitrary runtime control flow. The adversarial Node tests run separately with `npm run test:architecture` in CI.

The implementation follows [ESLint's local-plugin guidance](https://eslint.org/docs/latest/use/configure/plugins) and uses the installed [TypeScript compiler's module resolver](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API#customizing-module-resolution), avoiding a new dependency or a second alias mapping.

## Canonical content and domain rules

`src/content/questionBank.generated.json` is the versioned canonical content store. Its schema-v4 records use compact type-prefixed IDs (`s*`, `q*`, `i*`) and contain display-ready GFM/KaTeX stems and rationales, canonical choices, answer provenance, and optional rationale metadata such as sources and answer-review notes. The stored shape uses the minimal relationship chain of `question.quizId -> quiz.subjectId`; question order within each quiz is canonical array order. `src/content/schema/schema.ts` defines the storage contract, while `src/content/local/questionBank.ts` is its read-only JSON repository adapter: it hydrates sparse metadata, builds indexes, and derives quiz question counts before exposing the `QuizRepository` interface. `MarkdownContent` is the sole learner-facing content renderer. Stems and rationales use rich mode: `remark-math` parses math, raw HTML is parsed with `rehype-raw`, the shared restrictive `rehype-sanitize` policy runs before `rehype-katex`, and KaTeX CSS/fonts are bundled locally. `remarkMathPolicy.ts` preserves common currency prose from greedy dollar delimiter pairing. Choices, choice explanations, and sources retain restricted Markdown rendering. `richContentPolicy.ts` owns allowed HTML and image URLs, while `markdownValidation.ts` validates the same math and rich-content rules for canonical and staged content. `src/domain` holds pure quiz rules and types. `src/persistence` implements local storage behind repository interfaces. Completed attempt history is capped at 200 entries, while completion counts plus each quiz's lowest and latest scores remain durable in the progress envelope so those analytics survive history pruning. A separate per-quiz activity summary records the latest saved or completed use for subject-screen ordering; older browser data falls back to an active attempt's start time or latest completed score. Active attempts include an optional stable current-question ID plus persisted accumulated active time and a running-session timestamp, allowing the UI to resume both progress and the stopwatch. Fast Feedback pauses its persisted timer when all canonical questions have locked answers; resuming a fully answered attempt keeps it paused while the learner reviews. Legacy attempts without the timing fields remain compatible through the domain timing helpers. `src/analytics` aggregates structured completed attempts.

Flashcard content has a separate schema-v2 JSON store at `src/content/flashcardBank.generated.json`. It owns decks and cards, while `questionBank.generated.json` remains the only subject catalog. Its minimal relationship chain is `card.deckId -> deck.subjectId -> subject.id`; the read-only `flashcardBank.ts` adapter indexes parent membership and derives card counts. Subject catalogs retain canonical deck-array order. `migrateFlashcardBankV1` creates a reviewed candidate when migrating populated v1 data and preserves deck/card IDs and order. The combined `flashcardValidation.ts` gate checks structural references, rich content and duplicate sibling names for canonical validation and admin staging/replay. Flashcard progress uses its own versioned localStorage repository and is never quiz attempt data. Each deck's SHA-256 signature is computed once during launch; schema-v2 checkpoints then store only its current card ID plus opened and flagged card IDs. Schema-v1 position checkpoints are read in memory with empty opened/flagged sets, retain their old key unchanged, and migrate on the next successful write. Opening and flagging use the same optimistic revision checks and repository abstraction as position changes. Removing the topic layer leaves ordered deck study content unchanged, so saved positions remain resumable. Empty and removed decks are excluded from active selectors while their checkpoints remain recoverable.

## Application composition

`src/shared/theme.ts` owns the learner/admin theme. Reusable presentation lives under `src/shared/ui`: shell/brand, loading and recovery, transitions, generic notifications, rich-content rendering, shared catalog layouts, and shared study framing/navigation scrolling. These modules receive data and callbacks and do not import learner composition, feature modules, or admin. Content-error message mapping stays with loading/recovery presentation, outside the generic toast provider. Rich rendering uses the existing content sanitization/math policies and bundles KaTeX styles/fonts locally. Tests remain colocated with the shared modules.

Learner drawer policy and drawer helpers remain under `src/app/components`. Quiz screens, session hooks, selectors, feedback, results, and celebrations live under `src/features/quizzes`; flashcard screens, session hooks, selectors, and study controls live under `src/features/flashcards`. Each feature owns its session view contract in `session/navigation.ts`; app navigation composes those contracts and owns screen identity. Features do not import app or sibling features. The five catalog components reused by both features live under `src/shared/ui/catalog`; quiz-only statistics cards remain with quizzes. `src/app/lazyScreens.tsx` retains dynamic screen imports and preload wiring without feature barrels. Admin and development QA import reusable UI directly from `src/shared`; neither obtains generic presentation through learner app composition.

### Shell, navigation, and notifications

The learner shell keeps `AppNavigationDrawer` mounted outside screen transitions and owns only ephemeral expansion state. `View` includes a Flashcards destination, while drawer section selection is derived from the current view. Navigation requests from active quizzes and read-only result review pass through the existing exit confirmations; the session commits the requested dashboard only after the corresponding save or clear succeeds. The admin continues to use the header-only `AppShell` mode.

Reusable drawer presentation lives in `src/app/components/drawer`: `DrawerSurface` separates scrollable content from its edge control, and `DrawerEdgeToggle` owns the shared full-height hit target, arrow, hover/focus line, accessible state, and reduced-motion styling. It receives navigation-free toggle callbacks; application state and responsive drawer policy remain in `AppNavigationDrawer`.

The learner App owns a reusable toast provider outside screen transitions. Its portal host manages keyed notifications, positions, severity, actions, optional TTLs, and global or screen-scoped lifetime. App reports committed `screenIdentity` changes to the provider; screen-scoped toasts exit when their key is no longer current, while global toasts remain. Toasts fade on entry and exit, and reduced-motion preferences remove the transition. The guarded question-launch coordinator reports only current request failures to the composition layer; the layer converts them to safe persistent, subject-screen-scoped notifications without coupling UI to loading logic. Notification state stays in memory and does not write learner progress.

### Screens and session coordination

`ReadOnlyQuizChrome` and `ReadOnlyChoiceList` provide the shared header, footer, and answer presentation for Browse Answers and completed results review. They receive display data and callbacks, with no attempt mutation or persistence. `QuestionTile` supplies the existing navigator tile presentation to Browse, while `QuestionNavigator` keeps active and review filter sets. `FeedbackPanel` accepts optional read-only status for review and unavailable-answer cases; its default path preserves active Fast Feedback presentation. `ChoiceExplanations` renders optional per-choice rationales in both read-only screens.

`src/app/App.tsx` composes top-level navigation. Pure selectors in `src/features/quizzes/selectors/progress.ts` build dashboard subject summaries and per-subject quiz progress from repository interfaces and completed attempts, keeping storage reads and analytics out of screens. Its screen components receive data and callbacks, and reusable feedback and quiz components own presentation only. The subject screen owns transient setup-dialog state for a selected new or retaken quiz; setup is not a navigation view. The quiz and answer-browse screens share a responsive question-navigation frame and scroll-to-current primitive while retaining their mode-specific question controls. The answer-browse view is transient navigation state with a quiz and question index only; it reads canonical questions but never creates an attempt or calls the attempt repository, so browsing does not affect activity ordering or analytics. `src/features/quizzes/session/useQuizSession.ts` coordinates attempt transitions, page-hide pausing, legacy response normalization, and repository writes through the domain and repository interfaces. This keeps screens independent from `localStorage` and leaves room for a future repository implementation.

`useQuizLaunch` owns question-load deduplication, navigation generation, retry actions, and cancellation. It accepts a question-loader interface and calls the session only after current questions load. `lazyScreens.tsx` splits Quiz, Browse Answers, and Results presentation from the dashboard bundle; the relevant chunk starts preloading beside a question request, and Results preloads while a quiz is active. A screen boundary shows loading and a reload action if a chunk fails. The bootstrap entry similarly renders a reload action if its dynamic App import fails. These recovery messages contain no raw error details.

### Transient views and screen presentation

Exam-results review carries the just-completed attempt in transient navigation state. It reveals its responses without repository writes and is discarded after a confirmed exit.

`screenIdentity` in `src/app/navigation.ts` defines stable top-level destinations without including per-question progress or timer updates. `ScreenTransition` in `src/shared/ui/transitions/ScreenTransition.tsx` applies the shared entry animation at the composition boundary in `App.tsx`; the header and global exit dialog remain outside it. Screen content is replaced immediately, and reduced-motion preferences disable the animation.

`AppShell` keeps the learner header visible during the entry module import and lazy screen suspension. `ScreenLoading` supplies the centered accessible pending presentation; `ScreenLoadBoundary` owns suspense fallback and lazy screen failure recovery. Content receives a brief opacity entry only when the fallback was committed. The admin uses the same shell and loading presentation for its local bank snapshot wait. Resource-specific catalog skeletons and question-launch indicators remain in their screens.

`ResultsScoreHero` owns the decorative ring and score counter. A single request-animation-frame timeline drives both from the stored result percentage, while `ResultsScreen` remains responsible for the result summary and exact-score celebration.

Dashboard subject summaries live in `src/features/quizzes/selectors/dashboard.ts`. `App.tsx` composes the existing quiz and attempt repositories into those summaries; presentation components receive the resulting data and never read local storage. The active-subject carousel filters and orders only summaries that have saved active attempts, and `embla-carousel-react` owns its responsive scrolling, looping, and drag behavior.

## Progress and persistence

Learner progress uses a validated schema-v2 envelope under `meducation.progress.v2` through `LocalAttemptRepository`. Six legacy v1 keys are read as migration input and retained untouched after the first successful v2 write. A single storage write commits completed history, durable counts and scores, activity, completed IDs, and removal of the matching active attempt. History is capped at 200 records; completed IDs remain durable so repeated submissions cannot inflate counts after pruning. New active attempts record an exact signature of ordered question stems, choices, source answers, and verified answers, plus a bank revision for diagnostics. A legacy or changed-content active attempt requires an explicit restart before scoring. Stale repository instances detect a changed storage revision before saving and direct the learner to reload. This optimistic check is not an atomic cross-tab lock; a truly simultaneous read/write race remains possible. The browser storage event provides reactive cross-tab updates.

The repository caches a deeply frozen progress snapshot. Getters and dashboard/subject selectors share it until a local write or relevant browser `storage` event invalidates it; getters never migrate storage. React subscribes through `useSyncExternalStore`, so local writes and cross-tab changes refresh progress without rerendering from repeated storage reads. `createProgressView` groups retained completed scores by quiz and subject, and derives activity fallbacks once per snapshot. Cross-tab updates change the displayed snapshot but preserve the original edit revision, so a stale editing tab still refuses its next save and asks for reload. The optimistic simultaneous-write limit remains.

## Content API and loading

Quiz content is served through the read-only FastAPI service from the same canonical `src/content/questionBank.generated.json`; the service does not keep a second bank copy or publish edits. The dashboard requests a lightweight subject catalog containing quiz membership IDs and counts, then requests a subject's quiz details only when selected. Ordered question IDs and question text are delivered only with a selected subject and quiz. `src/content/api/runtimeQuestionBank.ts` validates that membership is present before exposing the catalog, tracks each resource's loading, retrying, ready, and error states, deduplicates requests, and keeps a revision-scoped in-memory cache observable by React. A shared client applies a 15-second deadline to every request attempt, retries only transient network, timeout, and selected HTTP failures, and uses bounded exponential backoff with jitter. The subject catalog and each subject quiz catalog expose their pending retry deadline and can advance only their own backoff wait without creating another request chain, allowing their banners to present a truthful countdown and Retry now action. Subject recovery is tracked per subject and remains visible across retry waits and active attempts until that catalog succeeds. Retry-After minimums disable Retry now until the server's requested delay elapses. Retry counts and delays are configured at Vite build time through `VITE_CONTENT_MAX_RETRIES`, `VITE_CONTENT_RETRY_BASE_DELAY_MS`, and `VITE_CONTENT_RETRY_MAX_DELAY_MS`. Abandoned question launches cancel their request or backoff wait. Learner messages map internal errors to safe copy; diagnostic categories and HTTP status codes are logged for developers only. The API computes and caches the content revision once as it loads the JSON snapshot. `VITE_CONTENT_SOURCE=local` explicitly selects the existing browser JSON adapter for offline development and QA. Attempts, scoring, timers, progress, and history remain in `LocalAttemptRepository`, `src/domain/quizEngine.ts`, and browser localStorage. The admin editor continues to export reviewed JSON for replacement of the canonical file; restart the API to load a replacement.

Flashcards extend this read-only service using `src/content/flashcardBank.generated.json`. Startup validates both files together and checks direct deck references against the shared subject catalog. A separate flashcard revision covers the flashcard bank and subject records, without changing the quiz revision. The learner loads flashcard subject counts and empty-deck membership on entry, a selected subject's deck summaries on demand, and ordered card bodies only when a deck starts. `RuntimeFlashcardBank` checks revisions, ownership, counts, and ordered card IDs, deduplicates resource requests, and cancels abandoned loads. The session guards every asynchronous launch with a token, so later navigation or deck selection prevents stale loads from saving progress or reopening study. Current card-request failures are reported to App for a persistent screen-scoped toast; retrying uses the original deck action. The subject catalog uses the shared warm wave skeleton and selected deck loads use the shell progress bar. Local mode exposes the same catalog through the JSON adapter. Flashcard checkpoints remain separate from quiz attempts.

`src/content/api/apiDecoders.ts` checks API catalog membership and order, question ownership, choice and answer references, and nested metadata before runtime content enters the cache. It hydrates only the domain's missing `metadata` field after validation. The Python bank loader validates the stored shape with typed nested metadata, and the API constructs response models explicitly while preserving omitted optional fields. Both use the same canonical JSON and revision serialization; shared fixtures in `tests/fixtures` check their contract parity. The backend's `QuestionBankRepository` protocol covers all route reads, with the JSON adapter injected at app creation. Conditional responses check revision and ETag before building a response body.

`contentTransport.ts` owns timeout, cancellation, retry classification, backoff, and safe request diagnostics. `RuntimeQuestionBank` receives that transport through its constructor and keeps resource state and request deduplication; `runtimeContentCache.ts` stores indexed subjects, quizzes, and ordered questions. API decoders remain the unknown-data boundary. Reconfiguration advances a generation counter so responses from an older revision or source cannot populate the current cache.

## Local authoring

`/admin.html` is a separate local-development JSON authoring tool. `useAdminEditor` owns editing commands, state, initial snapshot loading, stale-preview guards, busy/error handling, and the unsaved-change warning. `AdminApp` composes the navigator, editor, and status panels. The tool does not modify the learner UI, browser attempts, or repository files: it stages change sets in memory, validates the entire schema-v4 bank through the same content checks, and downloads a deterministic replacement bank plus its review change set. Its `AdminQuestionBankGateway` is an asynchronous seam; `QuizRepository` remains learner-facing and read-only. Vite omits the admin entry from normal production builds; set `VITE_BUILD_ADMIN=true` to opt in to bundling it.

## Entry points and deployment modes

`src/main.tsx` bootstraps the learner through `index.html`. API delivery is the default; the Vite development/preview proxy routes `/api` to the configured content service. Production hosting must route the same prefix to FastAPI. `VITE_CONTENT_SOURCE=local` explicitly selects the dynamically imported browser JSON adapters. Both modes retain local progress storage and the same domain contracts. Follow [frontend setup](../README.md) and [backend setup](../backend/README.md) for exact commands and environment variables.

`admin.html` is a separate development entry. Normal production builds omit it. To preview an enabled production editor, set both `VITE_BUILD_ADMIN=true` and `VITE_ENABLE_ADMIN=true` at build time; the bundling and runtime gates are independent. `/#content-qa` is development-only. The API does not publish edits: replace reviewed canonical JSON explicitly and restart the service to load it.

The runtime never calls a generative AI service. Quiz rules and scoring stay in the pure TypeScript domain layer; learner progress persists through the browser repository. The Python API owns read-only quiz content delivery from the canonical JSON file. A database adapter is an option if content delivery later needs one; no database migration is part of the current architecture.
