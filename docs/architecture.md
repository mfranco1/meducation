# Architecture

## Learner navigation and progress

Exam-results review carries the just-completed attempt in transient navigation state. It reveals its responses without repository writes and is discarded after a confirmed exit.

`screenIdentity` in `src/app/navigation.ts` defines stable top-level destinations without including per-question progress or timer updates. `ScreenTransition` in `src/app/components/ScreenTransition.tsx` applies the shared entry animation at the composition boundary in `App.tsx`; the header and global exit dialog remain outside it. Screen content is replaced immediately, and reduced-motion preferences disable the animation.

`AppShell` keeps the learner header visible during the entry module import and lazy screen suspension. `ScreenLoading` supplies the centered accessible pending presentation; `ScreenLoadBoundary` owns suspense fallback and lazy screen failure recovery. Content receives a brief opacity entry only when the fallback was committed. The admin uses the same shell and loading presentation for its local bank snapshot wait. Resource-specific catalog skeletons and question-launch indicators remain in their screens.

`ResultsScoreHero` owns the decorative ring and score counter. A single request-animation-frame timeline drives both from the stored result percentage, while `ResultsScreen` remains responsible for the result summary and exact-score celebration.

Dashboard subject summaries live in `src/app/dashboard.ts`. `App.tsx` composes the existing quiz and attempt repositories into those summaries; presentation components receive the resulting data and never read local storage. The active-subject carousel filters and orders only summaries that have saved active attempts, and `embla-carousel-react` owns its responsive scrolling, looping, and drag behavior.

Learner progress uses a validated schema-v2 envelope under `meducation.progress.v2` through `LocalAttemptRepository`. Six legacy v1 keys are read as migration input and retained untouched after the first successful v2 write. A single storage write commits completed history, durable counts and scores, activity, completed IDs, and removal of the matching active attempt. History is capped at 200 records; completed IDs remain durable so repeated submissions cannot inflate counts after pruning. New active attempts record an exact signature of ordered question stems, choices, source answers, and verified answers, plus a bank revision for diagnostics. A legacy or changed-content active attempt requires an explicit restart before scoring. Stale repository instances detect a changed storage revision before saving and direct the learner to reload. This optimistic check is not an atomic cross-tab lock; a truly simultaneous read/write race remains possible. The browser storage event provides reactive cross-tab updates.

The repository caches a deeply frozen progress snapshot. Getters and dashboard/subject selectors share it until a local write or relevant browser `storage` event invalidates it; getters never migrate storage. React subscribes through `useSyncExternalStore`, so local writes and cross-tab changes refresh progress without rerendering from repeated storage reads. `createProgressView` groups retained completed scores by quiz and subject, and derives activity fallbacks once per snapshot. Cross-tab updates change the displayed snapshot but preserve the original edit revision, so a stale editing tab still refuses its next save and asks for reload. The optimistic simultaneous-write limit remains.

## Canonical content and domain rules

`src/content/questionBank.generated.json` is the versioned canonical content store. Its schema-v4 records use compact type-prefixed IDs (`s*`, `q*`, `i*`) and contain display-ready GFM/KaTeX stems and rationales, canonical choices, answer provenance, and optional rationale metadata such as sources and answer-review notes. The stored shape uses the minimal relationship chain of `question.quizId -> quiz.subjectId`; question order within each quiz is canonical array order. `src/content/schema.ts` defines the storage contract, while `src/content/questionBank.ts` is its read-only JSON repository adapter: it hydrates sparse metadata, builds indexes, and derives quiz question counts before exposing the `QuizRepository` interface. `MarkdownContent` is the sole learner-facing content renderer. Stems and rationales use rich mode: `remark-math` parses math, raw HTML is parsed with `rehype-raw`, the shared restrictive `rehype-sanitize` policy runs before `rehype-katex`, and KaTeX CSS/fonts are bundled locally. `remarkMathPolicy.ts` preserves common currency prose from greedy dollar delimiter pairing. Choices, choice explanations, and sources retain restricted Markdown rendering. `richContentPolicy.ts` owns allowed HTML and image URLs, while `markdownValidation.ts` validates the same math and rich-content rules for canonical and staged content. `src/domain` holds pure quiz rules and types. `src/persistence` implements local storage behind repository interfaces. Completed attempt history is capped at 200 entries, while completion counts plus each quiz's lowest and latest scores remain durable in the progress envelope so those analytics survive history pruning. A separate per-quiz activity summary records the latest saved or completed use for subject-screen ordering; older browser data falls back to an active attempt's start time or latest completed score. Active attempts include an optional stable current-question ID plus persisted accumulated active time and a running-session timestamp, allowing the UI to resume both progress and the stopwatch. Fast Feedback pauses its persisted timer when all canonical questions have locked answers; resuming a fully answered attempt keeps it paused while the learner reviews. Legacy attempts without the timing fields remain compatible through the domain timing helpers. `src/analytics` aggregates structured completed attempts.

## Application composition

The learner shell keeps `AppNavigationDrawer` mounted outside screen transitions and owns only ephemeral expansion state. `View` includes a Flashcards destination, while drawer section selection is derived from the current view. Navigation requests from active quizzes and read-only result review pass through the existing exit confirmations; the session commits the requested dashboard only after the corresponding save or clear succeeds. The admin continues to use the header-only `AppShell` mode.

Reusable drawer presentation lives in `src/app/components/drawer`: `DrawerSurface` separates scrollable content from its edge control, and `DrawerEdgeToggle` owns the shared full-height hit target, arrow, hover/focus line, accessible state, and reduced-motion styling. It receives navigation-free toggle callbacks; application state and responsive drawer policy remain in `AppNavigationDrawer`.

The learner App owns a reusable toast provider outside screen transitions. Its portal host manages keyed notifications, positions, severity, actions, optional TTLs, and global or screen-scoped lifetime. App reports committed `screenIdentity` changes to the provider; screen-scoped toasts exit when their key is no longer current, while global toasts remain. Toasts fade on entry and exit, and reduced-motion preferences remove the transition. The guarded question-launch coordinator reports only current request failures to the composition layer; the layer converts them to safe persistent, subject-screen-scoped notifications without coupling UI to loading logic. Notification state stays in memory and does not write learner progress.

`ReadOnlyQuizChrome` and `ReadOnlyChoiceList` provide the shared header, footer, and answer presentation for Browse Answers and completed results review. They receive display data and callbacks, with no attempt mutation or persistence. `QuestionTile` supplies the existing navigator tile presentation to Browse, while `QuestionNavigator` keeps active and review filter sets. `FeedbackPanel` accepts optional read-only status for review and unavailable-answer cases; its default path preserves active Fast Feedback presentation. `ChoiceExplanations` renders optional per-choice rationales in both read-only screens.

`src/app/App.tsx` composes top-level navigation. Pure selectors in `src/app/progress.ts` build dashboard subject summaries and per-subject quiz progress from repository interfaces and completed attempts, keeping storage reads and analytics out of screens. Its screen components receive data and callbacks, and reusable feedback and quiz components own presentation only. The subject screen owns transient setup-dialog state for a selected new or retaken quiz; setup is not a navigation view. The quiz and answer-browse screens share a responsive question-navigation frame and scroll-to-current primitive while retaining their mode-specific question controls. The answer-browse view is transient navigation state with a quiz and question index only; it reads canonical questions but never creates an attempt or calls the attempt repository, so browsing does not affect activity ordering or analytics. `src/app/session/useQuizSession.ts` coordinates attempt transitions, page-hide pausing, legacy response normalization, and repository writes through the domain and repository interfaces. This keeps screens independent from `localStorage` and leaves room for a future repository implementation.

`useQuizLaunch` owns question-load deduplication, navigation generation, retry actions, and cancellation. It accepts a question-loader interface and calls the session only after current questions load. `lazyScreens.tsx` splits Quiz, Browse Answers, and Results presentation from the dashboard bundle; the relevant chunk starts preloading beside a question request, and Results preloads while a quiz is active. A screen boundary shows loading and a reload action if a chunk fails. The bootstrap entry similarly renders a reload action if its dynamic App import fails. These recovery messages contain no raw error details.

The runtime never calls a generative AI service. Quiz rules and scoring stay in the pure TypeScript domain layer; learner progress persists through the browser repository. The Python API owns read-only quiz content delivery from the canonical JSON file. A database adapter is an option if content delivery later needs one; no database migration is part of the current architecture.

## Content API and loading

Quiz content is served through the read-only FastAPI service from the same canonical `src/content/questionBank.generated.json`; the service does not keep a second bank copy or publish edits. The dashboard requests a lightweight subject catalog containing quiz membership IDs and counts, then requests a subject's quiz details only when selected. Ordered question IDs and question text are delivered only with a selected subject and quiz. `src/content/runtimeQuestionBank.ts` validates that membership is present before exposing the catalog, tracks each resource's loading, retrying, ready, and error states, deduplicates requests, and keeps a revision-scoped in-memory cache observable by React. A shared client applies a 15-second deadline to every request attempt, retries only transient network, timeout, and selected HTTP failures, and uses bounded exponential backoff with jitter. The subject catalog and each subject quiz catalog expose their pending retry deadline and can advance only their own backoff wait without creating another request chain, allowing their banners to present a truthful countdown and Retry now action. Subject recovery is tracked per subject and remains visible across retry waits and active attempts until that catalog succeeds. Retry-After minimums disable Retry now until the server's requested delay elapses. Retry counts and delays are configured at Vite build time through `VITE_CONTENT_MAX_RETRIES`, `VITE_CONTENT_RETRY_BASE_DELAY_MS`, and `VITE_CONTENT_RETRY_MAX_DELAY_MS`. Abandoned question launches cancel their request or backoff wait. Learner messages map internal errors to safe copy; diagnostic categories and HTTP status codes are logged for developers only. The API computes and caches the content revision once as it loads the JSON snapshot. `VITE_CONTENT_SOURCE=local` explicitly selects the existing browser JSON adapter for offline development and QA. Attempts, scoring, timers, progress, and history remain in `LocalAttemptRepository`, `src/domain/quizEngine.ts`, and browser localStorage. The admin editor continues to export reviewed JSON for replacement of the canonical file; restart the API to load a replacement.

`src/content/apiDecoders.ts` checks API catalog membership and order, question ownership, choice and answer references, and nested metadata before runtime content enters the cache. It hydrates only the domain's missing `metadata` field after validation. The Python bank loader validates the stored shape with typed nested metadata, and the API constructs response models explicitly while preserving omitted optional fields. Both use the same canonical JSON and revision serialization; shared fixtures in `tests/fixtures` check their contract parity. The backend's `QuestionBankRepository` protocol covers all route reads, with the JSON adapter injected at app creation. Conditional responses check revision and ETag before building a response body.

`contentTransport.ts` owns timeout, cancellation, retry classification, backoff, and safe request diagnostics. `RuntimeQuestionBank` receives that transport through its constructor and keeps resource state and request deduplication; `runtimeContentCache.ts` stores indexed subjects, quizzes, and ordered questions. API decoders remain the unknown-data boundary. Reconfiguration advances a generation counter so responses from an older revision or source cannot populate the current cache.

## Local authoring

`/admin.html` is a separate local-development JSON authoring tool. `useAdminEditor` owns editing commands, state, initial snapshot loading, stale-preview guards, busy/error handling, and the unsaved-change warning. `AdminApp` composes the navigator, editor, and status panels. The tool does not modify the learner UI, browser attempts, or repository files: it stages change sets in memory, validates the entire schema-v4 bank through the same content checks, and downloads a deterministic replacement bank plus its review change set. Its `AdminQuestionBankGateway` is an asynchronous seam; `QuizRepository` remains learner-facing and read-only. Vite omits the admin entry from normal production builds; set `VITE_BUILD_ADMIN=true` to opt in to bundling it.
