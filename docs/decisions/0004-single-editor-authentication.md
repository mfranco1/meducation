# Single-editor authentication and private admin sessions

Status: security/session contract selected; ZITADEL Cloud is the provisional OIDC adapter candidate, final adapter acceptance pending before L4. Provider account/configuration and hosted tests are deferred. Observed 2026-10-13. Gate: [L0 Step 8](../work/done/L0-local-contracts-plan.md). Local learner progress remains unauthenticated and in the browser.

## Current boundary and proposed ownership

At contract selection, [AdminApp](../../src/admin/AdminApp.tsx) creates an in-memory gateway from bundled canonical JSON. Its development/build enable flag is not authorization. [FastAPI](../../backend/src/meducation_api/main.py) serves read-only public content; [settings](../../backend/src/meducation_api/settings.py) has no identity/session settings. Nothing here implements authentication or changes content authority.

L4 adds a backend-for-frontend boundary: admin UI and `/api/admin/*` use one trusted origin, backend OIDC code exchange and an opaque server session. All private reads, drafts, save/undo/reset, publish/activate/rollback, exports and diagnostics authorize on the server; learner published-content endpoints remain public and ignore admin cookies. The authenticated editor is the exact configured `(issuer, subject)` pair, never email, domain, display name, a browser admin flag, or a generic provider role. Registration never grants editor access. Use the existing editor/core with an HTTP gateway; remove bundled private draft bootstrap from the hosted editor.

Proposed backend modules: `backend/src/meducation_api/auth/` owns OIDC validation, provider assurance adapter, session store and authorization dependencies; admin route/gateway modules consume a verified principal. `src/admin/data` owns credentialed HTTP/CSRF transport; admin composition owns login/session-expiry UX. Shared presentation and learner features do not gain auth dependencies. This single-editor contract does not implement paid learner accounts.

## Provider capability evidence and decision

**Neon managed Auth:** current official source names it Managed Better Auth, distinct from the legacy Stack Auth integration. It supports a managed subset of Better Auth plugins, including JWT and Admin, but its roadmap lists MFA as coming soon. Underlying Better Auth's own plugin support is not evidence that Neon exposes it. Native Data API JWT support does not establish our FastAPI OIDC code-flow/MFA contract. Do not select Neon Auth for privileged authoring on that evidence. This is a current capability gap, not a permanent rejection or a reason to change the Postgres provider. [Overview](https://github.com/neondatabase/website/blob/main/content/docs/auth/overview.md), [managed plugins](https://github.com/neondatabase/website/blob/main/content/docs/auth/guides/plugins.md), [roadmap](https://github.com/neondatabase/website/blob/main/content/docs/auth/roadmap.md).

**ZITADEL Cloud:** official documentation supports code flow with S256 PKCE, issuer discovery/JWKS, RS256, hosted login, forced MFA, and ID-token `amr`, `auth_time` and `sid`. The documented assurance example includes `mfa`; access tokens do not contain these assurance claims. Organization policies can override defaults, and forcing local-only MFA does not enforce it for external identity providers. The first candidate uses a directly invited local editor, disables registration/social/external login for this app, and enables organization-specific forced MFA using password plus TOTP or a security key. Do not accept email/SMS OTP or assume a passkey establishes the chosen MFA policy without adapter evidence. [Code flow](https://zitadel.com/docs/guides/integrate/login/oidc/login-users), [claims](https://zitadel.com/docs/apis/openidoauth/claims), [policies](https://zitadel.com/docs/guides/manage/console/default-settings), [keys](https://zitadel.com/docs/guides/integrate/login/oidc/webkeys).

The published Cloud Free plan currently includes all security features and 100 daily active users, sufficient in count for one editor; Pro starts at $100/month. This is a candidate cost fit, not a guaranteed production entitlement/SLA, email delivery or future price. Verify terms, available region, quotas and recovery before signup. Self-hosting an identity server would add maintenance and is not selected. [Cloud pricing](https://zitadel.com/pricing).

Final adapter acceptance is **pending**: verify the chosen tenant's exact MFA method/claim mapping, effective organization policy, forced fresh factor challenge on reauthentication, client authentication method and account recovery. Documentation alone cannot prove these configured behaviors. Until then L0-C records the contract/capability status, but L4 cannot ship a provider-specific production adapter or weaken assurance. L1–L3 are not blocked. A later managed OIDC candidate must meet the same gates; no custom password/MFA system is proposed.

## Login and token validation contract

Use a maintained Python OIDC/JWT library, with its Python 3.14 dependency/crypto support checked and pinned during L4. Do not hand-roll JWT signatures or OAuth protocol processing.

1. Backend creates a bounded single-use login transaction (10-minute expiry) containing random state, nonce, PKCE verifier/S256 challenge, fixed callback and purpose (initial login or reauthentication). Use at least 32 random bytes for state/nonce/browser binding; store secret verifier server-side. A host-only HttpOnly SameSite=Lax transaction cookie binds the callback to the initiating browser. Keep a bounded number of transactions; rate-limit initialization/callback. Login initiation is same-origin POST with an anonymous CSRF token; callback is the explicitly exempt OIDC GET with validated transaction binding, not a general CSRF exemption.
2. Authorization requests use code response mode query, scopes `openid` only initially, `prompt=login` and `max_age=0`. No implicit/password flow or `offline_access`; no automatic refresh grant. PKCE is required even for a confidential web client. Token endpoint client authentication must be pinned to the verified provider-supported method; prefer client_secret_basic for the initial web-client adapter, subject to evidence. Secret stays backend-only. HTTPS endpoints/redirects are fixed configuration; no URL derived from untrusted Host/forwarded headers or token claims. Local HTTP exceptions are explicit loopback development only.
3. Callback checks bounded inputs, exactly one state/code, transaction cookie/purpose/expiry and single-use consumption. Exchange code once with the original redirect URI/verifier; errors/replay clear the transaction and grant no session. Reauthentication must return the same issuer/subject as the current session. Failed/canceled reauthentication retains an existing still-valid session but never upgrades freshness or resends a write.
4. Validate the signed ID token obtained from that exchange: exact configured issuer; audience includes admin client ID; require matching azp when multiple audiences and reject any mismatching supplied azp. Require nonempty sub, exp, iat, nonce and auth_time; require supported numeric dates; validate optional nbf. Require not expired, no future iat/auth_time beyond 60-second clock skew, auth_time consistent with iat, correct nonce and authentication age <=5 minutes on initial/step-up callback. Require RS256 and RSA signing key >=2048 bits for the first adapter. Reject none/HS algorithms, algorithm/key confusion, malformed/oversized tokens, duplicate claims and unsupported assurance. Apply other required library/OIDC checks for this flow. An access token or logout token cannot substitute for an ID token.
5. Fetch keys only from the configured HTTPS issuer's verified discovery/JWKS endpoint, with fixed host/endpoint allowlists, TLS verification, bounded response size/timeouts and no arbitrary redirects. Never follow token jku/x5u to fetch keys. Cache validated keys up to 15 minutes; on unknown kid refresh once, rate-limited/coalesced. An unavailable refresh, ambiguous kid, stale cache or invalid signature denies new login; no disabling validation. Existing app sessions follow their own expiry/revocation contract, not the life of a JWT cache. Test actual signing-key rotation with overlap and removal.
6. Adapter maps signed provider evidence into `VerifiedEditorIdentity`: issuer/sub, provider sid, auth_time, assurance policy ID and assurance-observed time. Require amr array containing the provider-documented `mfa` marker for the ZITADEL candidate, plus the verified effective policy restricting permitted factors. No universal acr interpretation or guessed “passkey == MFA” rule. An account merely enrolling MFA is insufficient. The marker alone does not prove when a factor was challenged: forced reauth/factor remembrance configuration and hosted evidence must establish freshness before selecting this adapter.
7. Match the exact editor allowlist and enabled admin configuration before creating a session. No auto-provisioning from token email, no wildcard subject or bootstrap first-login privilege. Store an append-only audit identity `(issuer, sub)` with authored operations; treat names/email as optional display data only.

These local validation rules apply the [OIDC Core checks](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation). Provider `prompt`/`max_age` support is documented, but those parameters alone do not prove a fresh MFA challenge. [ZITADEL request parameters](https://zitadel.com/docs/apis/openidoauth/endpoints).

## Server session, expiry and revocation

Select a Postgres-backed private `admin_auth` session store, separate from content and all learner progress. Store hashes of opaque 32-byte random session identifiers, issuer/sub/provider sid, policy/config epoch, established assurance/fresh-auth time, created/last interactive activity/absolute expiry and revoked state. Login transactions are short-lived server-side records; encrypt any temporary retained token/secret material with an independently managed backend key. Ordinary sessions do not need retained access/refresh tokens. If an ID-token hint is required for provider sign-out, retain it encrypted for that limited lifetime; never log or expose it to app JavaScript.

Use a separate least-privilege session-store login allowed only the necessary admin_auth table operations, not content DDL/DML; the content editor role remains separate. Include migrations/session rows in DB recovery design. Store failure returns 503 and performs no admin operation; do not fall back to anonymous, stateless cookies or per-worker RAM. All workers use the same revocation state. No continuous SQL keepalive/sweeper is required; expired rows can be pruned on explicit administrative activity.

Cookie: `__Host-meducation-admin`, opaque value, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. Max-Age cannot exceed 8-hour absolute session lifetime; server enforces 30-minute idle expiry and 8-hour absolute expiry with no sliding extension of absolute expiry. Polling/healthchecks do not count as interactive activity. Cookie is sent to same-origin learner URLs too; public content ignores it and preserves public cache behavior. Loopback HTTP development uses a separately named non-__Host development cookie with explicit development settings; production cannot accept that cookie or insecure settings.

Rotate session ID/CSRF token at login and successful step-up, invalidate the old ID atomically, and clear cookie with matching attributes on logout/expiry. Publish, activate/rollback a release, bulk destructive draft operations and private full exports require provider-backed fresh authentication/verified MFA within 15 minutes; session creation from reused first-factor-only SSO does not reset MFA freshness. Do not replay a pending mutation automatically after reauthentication; show the draft/revision and require confirmation again. Ordinary save/read still requires a live verified-editor session.

Each protected request checks revocation/expiry, current editor allowlist and policy epoch. A deployment changing allowlist/assurance config revokes old sessions; emergency operator action revokes all sessions and disables admin access independently of provider availability. Restoring a DB snapshot can resurrect session records, so increment an externally configured auth epoch and clear login transactions after restore before serving admin traffic. No auth data goes into content JSON exports.

Local POST logout revokes the app session first, then clears cookie. Provider RP-initiated logout is optional follow-up using fixed allowlisted redirect/validated state; its failure never undoes local logout. It does not automatically prove global provider logout. If ZITADEL is selected, implement documented signed back-channel logout: validate issuer/audience/signature/events/time, no nonce, bounded replay-protected jti, and sid/sub mapping before revoking sessions. That server callback has signature authentication instead of browser CSRF. Test delivery, duplicates and forged/logout-vs-ID-token confusion. Provider account disable/reset need not immediately invalidate cached app sessions; absent a delivered event/operator revocation, access is bounded by the stated idle/absolute timeout, with sensitive writes requiring fresh authentication. [Back-channel logout](https://zitadel.com/docs/guides/integrate/back-channel-logout).

## Browser/API protections and editor UX

Every state-changing admin request, including logout, requires exact trusted Origin, supported JSON content type, a session-bound unpredictable CSRF token in a custom header and a valid session. Reject missing/mismatched Origin for browser mutation endpoints; same-site subdomains are not trusted automatically. GET/HEAD never change content. No credentialed wildcard CORS; prefer same-origin and disable admin cross-origin access. Cookie SameSite alone is insufficient; CSRF tokens stay in admin memory, never localStorage. Login/callback and signed back-channel endpoints have their own narrowly defined rules above. [CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

Private responses/auth callbacks use Cache-Control: no-store; public cache keys must not vary on/retain privileged tokens or private responses. Mask tokens/cookies/codes/passwords in application and reverse-proxy logs, including callback query strings. Callback returns a redirect immediately to a fixed clean admin URL with Referrer-Policy: no-referrer. Return-to is an allowlisted internal path, no absolute/protocol-relative/userinfo/backslash encodings. Callback host does not serve third-party assets. Configure trusted proxy hops/hosts explicitly; server-generated redirects use configured public origin.

Admin needs CSP/frame restrictions and existing safe rich-content rendering; HttpOnly cannot prevent same-origin XSS from acting as the editor. Server continues validating all payloads, reasons and revision preconditions independent of auth. Bound auth/body sizes and rate-limit login/callback/admin operations; use stable safe errors (401 session required/expired, 403 authorization/CSRF/assurance denied, 503 identity/session dependency unavailable), no raw provider error reflection. UI retains unsaved in-memory edits on expiry, blocks further requests and offers sign-in; it never silently publishes/discards them. Do not store private drafts or bearer tokens in learner persistence. [Session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

## Operator recovery and secrets

Before enabling hosted admin: invite only the configured editor, enroll primary and backup factors, verify recovery behavior, and securely retain provider recovery material/support procedures off-device. Protect the provider-management account with strong MFA too. Provider-managed reset/enrollment is separate from app authorization. No email-link-only admin bypass, shared permanent master token or local backdoor.

If locked out, recover through the provider's verified process while app admin remains disabled. A changed subject requires an explicit operator configuration update and global session epoch change; never match it automatically by reused email. Document a cold recovery path through deployment secrets/configuration and tested DB backups; preserve existing content/audit rather than resetting DB. Password/factor/client-secret changes require the appropriate app-session revocation and factor recheck; provider reset success alone is not evidence of local revocation.

Separate development and production OIDC clients/secrets/callbacks. Rotate client secret/encryption key using bounded overlap and explicit key IDs; audit completion and retire old secrets. Session identifiers are random and hashed, not signed with the client secret. Emergency rotation may invalidate all sessions/transactions. Production startup rejects missing issuer/client/editor subject/allowed origin, dev bypass, insecure cookies/HTTP provider URLs or wildcard callbacks; learner-only deployment can deliberately leave all admin routes disabled. Do not provision accounts, rotate secrets or send invitation emails in L0.

## Local test identity and verification gates

L4 unit/integration tests issue synthetic RS256 tokens from disposable test keys via injected OIDC/JWKS/clock/session ports, using the exact selected claims and negative cases. A loopback-only test OIDC service can exercise code/PKCE/state/cookie/redirect flow. It is not a custom production identity service or a no-auth header shortcut. Development issuer/subject and cookie settings must be visibly separate; require explicit development mode and loopback binding, and refuse them in production, including accidentally inherited environment variables. Account/MFA screens may be simulated locally but do not establish hosted assurance.

Pending L4 automated gates:

- Auth boundary: direct HTTP access to every private operation rejects anonymous, non-editor, expired/revoked/old-epoch sessions; learner published routes still work without identity availability. No private draft/artifact leakage in bundles/caches.
- Token faults: wrong issuer/audience/azp/nonce/sub; unsigned/HS/unsupported algorithm; wrong key/kid; malformed/oversized/duplicate claims; expired/future dates/missing auth_time; missing/weak MFA; access/logout-token substitution; key rotation and JWKS outage. Deny without mutation/session creation.
- Login/session: PKCE/state/cookie mismatch, callback/code replay, transaction expiry, cancel/error, session fixation/rotation, idle/absolute expiry, clock skew, DB outage/multi-worker revocation, DB restore epoch, concurrent step-up/logout and allowlist change. State consumption/session issuance and protected mutations must serialize safely; a write already committed before revocation cannot be retroactively undone.
- CSRF/transport: cross-site/sibling-origin mutation, missing Origin/header, wrong token/content type, logout CSRF, open-redirect/proxy-header attempts, query/log redaction, cookie flags and private no-store. Signature-protected back-channel logout validates its separate replay/purpose rules.
- Editor flow: preserve dirty draft on expired session, block saves, successful fresh step-up same subject, no automatic mutation replay, stale revision rejection after reauth, accessible login/errors/confirmation.
- Production guard: dev issuer/identity/token/header bypass/insecure cookies/missing required settings refuse startup with admin enabled; admin-disabled learner deployment remains valid.

Pending provider acceptance before L4 production adapter, and hosted release gates before launch:

- Demonstrate exact invited subject/client/issuer, registration disabled and effective forced allowed MFA; deny a valid token lacking required evidence. Record redacted claim shape/policy configuration without tokens, keys or personal data.
- Demonstrate fresh factor challenge with remembered SSO, prompt/max_age and sensitive-action step-up; verify assurance semantics/time, cancellation, another user's login and disabled-account behavior. Finalize adapter mapping only after this evidence, not by assuming auth_time measures last MFA.
- Exercise HTTPS reverse proxy, actual cookie/CSRF redirects, signing-key rotation, local/provider logout/back-channel revocation, provider/session-store outages, factor recovery, emergency disable and session epoch change. Confirm chosen plan entitlements/region/email delivery and recovery access; local mocks cannot close these gates.

L0-C contract/capability status is complete; final provider acceptance remains explicitly pending as permitted by L0. No authentication is implemented and no cloud configuration is created. Self-audit distinguished enrollment from challenged MFA, provider console MFA from application assurance, ID tokens from API bearer/logout tokens, local logout from provider revocation, and DB restoration from safe session revocation.
