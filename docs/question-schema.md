# Question schema

Defines the schema-v5 quiz document stored in paired drafts and releases and written to deterministic `questionBank.json` exports. Preserve array and choice order, exact authored strings, omitted optional fields, source and verified answers, and established IDs. The server assigns new IDs when a record is created ([content management](content-management.md#record-api-and-publication)).

The PostgreSQL quiz document and its deterministic `questionBank.json` exports have `schemaVersion: 5` and top-level `subjects`, `topics`, `quizzes`, and `questions` collections. IDs are compact, type-prefixed strings: subjects use `s*`, topics `t*`, quizzes `q*`, and questions `i*`. A topic is `{ id, subjectId, name }`; a quiz stores `topicId` and a question `quizId`, with no redundant subject IDs. Topics are ordered within their subject and may be empty. Questions are grouped by quiz in canonical array order; their position within each quiz determines the one-based learner display number. The database stores a zero-based global collection ordinal per table to reconstruct each array exactly ([ADR 0005](decisions/0005-paired-content-releases-and-postgres-schema.md)).

The `subjects` and `topics` collections are also the authoritative registry for flashcards: decks reference these stable topic IDs from the paired flashcard document; do not duplicate subjects or topics there. `question.metadata.topic` remains optional descriptive text and is unrelated to the topic records.

Each question has a stable ID, canonical GFM `stem`, ordered `choices`, answer provenance (`answer`, optional `verifiedAnswer`, and optional note), a required GFM `rationale`, optional `rationaleMeta`, and sparse optional metadata. Runtime scoring prefers `verifiedAnswer`, then `answer`. `answerSource` is not stored: a verified answer indicates verified provenance, otherwise the provided answer is used. `questionCount` is derived from the indexed questions and is not stored on a quiz.

Question text and choice order are canonical once recorded. Make content corrections directly in the record, review them carefully, and preserve their rationale in the relevant provenance or review field. Never regenerate IDs casually. IDs are opaque database identifiers; do not derive subject, quiz, ordering, or display meaning from them.

## Markdown and rationale metadata

`stem` and `rationale` are canonical GitHub Flavored Markdown with inline LaTeX in `$...$` and display math in `$$` blocks on separate lines. Fenced `math` blocks are also supported. Use `\$` for a literal dollar next to a number when it could be read as math; common currency amounts followed by prose (for example `$500B; its citizens...` or `$10 per item and $20 each`) are preserved as text. A dollar pair that looks like an amount ending in an incomplete arithmetic operation is preserved as text too. Use TeX such as `$600 \times 12$` for unambiguous numeric math. An unmatched delimiter and `\(...\)` or `\[...\]` remain literal. Ordinary fenced code and inline code are not interpreted as math.

Stems and rationales may also include a limited HTML subset: paragraphs, headings, emphasis, subscript, superscript, lists, blockquotes, tables, code, links, and images. Markdown image syntax and `<img>` are supported. Images require meaningful alt text and may use an app-local path such as `/content/figures/nerve.png`; approved HTTPS image origins are configured through `VITE_CONTENT_IMAGE_ORIGINS` for the app and `CONTENT_IMAGE_ORIGINS` for validation. Scripts, iframes, SVG, forms, event handlers, inline styles, arbitrary classes and IDs, unsafe link protocols, data URLs, and protocol-relative URLs are forbidden. `rationaleMeta.sources`, choices, and choice explanations remain restricted Markdown and do not render math. Content is validated at development time and sanitized at rendering time through one shared component; it is never rewritten by the browser. Math is rendered locally with KaTeX and bundled fonts; the sanitizer preserves only the allowlisted math marker classes needed by the rendering pipeline.

Use `rationaleMeta.provenance: 'source_migrated'` when a stored source rationale was normalized during a content migration, and `ai_draft_reviewed` only for a reviewed development-time AI draft. Such entries require `reviewedAt` and `reviewNote`. `rationaleMeta.sources` is shown in a disclosure below the rationale. The app never generates explanations at runtime.

When the answer key or question context is uncertain, `rationaleMeta.answerReviewNote` carries the explanation. The learner sees that note and the feedback status says the key is under review; the original `answer` remains unchanged. Such entries still require answer verification before their quiz scores can be treated as final.

`metadata` is omitted when no classification is known. Do not store default `difficulty: 'unknown'`, a duplicate discipline label, or an empty metadata object.
Optional fields are omitted rather than stored as `null`. The bank loader and authoring validator reject unknown nested metadata keys and malformed values. API responses preserve omitted optional fields; the browser hydrates a missing `metadata` field only after checking the response.

## Authoring input

Editors save complete stored entities through the paired HTTP draft; bulk adds use content-only JSON (see [content management](content-management.md#editor-workflow)). IDs cannot be renamed, deleting a subject or quiz with children requires explicit cascade review, and the final pair must pass the same validation as a stored release.
